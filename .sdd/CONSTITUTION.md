# プロジェクト原則

**バージョン**: 1.1.0
**最終更新日**: 2026-07-29
**ステータス**: 有効

## 目的

このドキュメントは、`minimax-cli` の開発を統制する非交渉原則を定義します。すべてのコード、仕様、設計判断はこれらの原則に従う必要があります。

このプロジェクトの存在理由は **認証情報の非露出** です。MiniMax の API トークンを AI エージェントに渡さずに音声ファイルを生成するために作っています。したがってセキュリティに関するビジネス原則が最上位に立ちます。

**一次情報の所在**: 値・コマンド・ジョブ名の一次情報はコードと設定ファイル（`Cargo.toml` / `rustfmt.toml` / `clippy.toml` / `deny.toml` / `ci.yml` / `dist-workspace.toml`）、運用手順の二次情報は `CLAUDE.md` です。この原則ファイルに具体値は書きません。食い違ったら **コードが正** です。

## 原則階層

```
1. ビジネス原則（最優先）
   ↓
2. アーキテクチャ原則
   ↓
3. 開発手法原則
   ↓
4. 技術制約
```

優先度が高い原則が低い原則に優先します。

## 原則サマリー

| ID | 原則 | 一言 |
|:---|:---|:---|
| **B-001** | 認証情報を AI エージェントの到達範囲に置かない | トークンを stdout・プロセス引数・ログ・環境変数に載せない。受け口は stdin のみ |
| **B-002** | stdout は成果物専用に保つ | stdout へ書く経路を許可リストで管理する。ログ・進捗・エラーは stderr |
| **A-001** | 境界層は薄く保ち、外部世界の読み取りをそこに閉じる | 環境変数・I/O の読み取りは境界の型に集約し、解決ロジックには引数で渡す |
| **A-002** | セキュリティに関わる仕組みを自作しない | TLS は rustls 固定、シークレット保存は OS 機構。暗号・認証を自作しない |
| **D-001** | 外形をテストで固定する | 全サブコマンドの終了コードと stdout / stderr の出し分けを結合テストで固定 |
| **D-002** | 新機能は仕様書から始める | 新規サブコマンド・外部 API 連携は PRD → spec → design を先に。軽微な変更は不要 |
| **T-001** | 実行時に落ちる余地を残さない | `unsafe` 禁止、`unwrap` / `expect` は実装で使わない、失敗は型で表現 |

> このサマリーは、`.rs` を編集するときに PreToolUse フックがこのファイルの **冒頭 3000 文字** を
> additionalContext として注入する（セッションにつき 1 回）ため、全原則の ID と要点が
> 注入範囲に入るように置いています。詳細は以下の各節を参照してください。

## 1. ビジネス原則（最優先）

### B-001: 認証情報を AI エージェントの到達範囲に置かない

**原則**: MiniMax の API トークンは CLI プロセス内で OS のセキュアな保存領域から読み出し、AI エージェントが読める経路（stdout・プロセス引数・会話ログ・環境変数）に一切載せない。

**適用範囲**: すべてのサブコマンド、ログ出力、エラーメッセージ、ドキュメントの例示

**検証方法**:

- [ ] トークンを stdout に出力する経路が存在しない
- [ ] 値を引数で受け取るフラグ（`--token <VALUE>` 等）が存在しない。受け口は stdin のみ
- [ ] エラーメッセージと `Display` / `Debug` 実装にトークンが載らない
- [ ] HTTP レイヤのログが `warn` より下に開かない。どんな directive を与えても貫通しない（グローバル指定 `trace` / 同名 target `hyper=trace` / 深い target `hyper::proto=trace` のすべてを `logging.rs` の `the_ceiling_cannot_be_bypassed_by_any_directive` が実際にイベントを流して固定している）
- [ ] 依存に新しい HTTP / TLS クレートを追加したとき、`logging.rs` の `HTTP_LAYER_CRATES` にも追加した（この配列はテストからも参照するため、追加すれば上限の検証対象に自動で入る）

**違反例**:

- `minimax token show` のようにトークンを stdout に出すサブコマンド
- `minimax tts --token sk-xxx` のようなフラグ。プロセス引数は他プロセスから読めるうえ、AI エージェントがコマンドを組み立てるとトークンが会話ログに永久に残る
- トークンを含む値を `{:?}` や `{}` でログに出す
- 認証情報を環境変数で渡す運用を README で推奨する。環境変数は子プロセスに継承されるため、AI エージェントのシェルツールから読める

**準拠例**:

- トークンの受け口を stdin に限定する
- トークンを保持する型の `Display` / `Debug` を封じる（`secrecy` 等）
- `logging.rs` で、環境変数由来の `EnvFilter` と HTTP レイヤを `warn` で打ち止めにする `filter::Targets` を `FilterExt::and` で AND 結合する。`Targets` は target を `::` 区切りの接頭辞で照合するため深い target にも効く（`add_directive` による後付け上書きは深い target で貫通するので使わない）

---

### B-002: stdout は成果物専用に保つ

**原則**: stdout には成果物（生成した音声ファイルのパス等）と機械可読な出力だけを書く。ログ・進捗・警告・エラーはすべて stderr に出す。AI エージェントは CLI の stdout をそのままコンテキストに取り込むため、余計なものを書かない。

**適用範囲**: すべてのサブコマンド、ライブラリ層、テスト

**検証方法**:

- [ ] 失敗時に stdout が空であることを結合テストで固定している
- [ ] `println!` の直接使用が `#![warn(clippy::print_stdout)]` で検出される
- [ ] stdout へ書く経路が下記の許可リストに載っているものだけである。新しい経路を追加するときは同時に許可リストへ追記する

**stdout への許可リスト**:

- clap の `--help` / `-h` 出力
- clap の `--version` / `-V` 出力
- （TTS 実装後）生成した音声ファイルのパス 1 行

**違反例**:

- 進捗表示やエラー詳細を stdout に出す
- 許可リストに追記せずに stdout へ書く経路を増やす
- `clippy::print_stdout` を `Cargo.toml` の `[lints.clippy]` に置く（テストターゲットにも適用され、テストに `println!` を書いた時点で CI が落ちるため、`src/main.rs` / `src/lib.rs` の `#![warn(...)]` 側に置く）

**準拠例**:

- `tracing` の出力先を stderr に向ける
- clap の `--help` / `--version` は利用者向けの正当な stdout 出力として扱う
- 成果物は `writeln!(std::io::stdout().lock(), "{}", path.display())?` で書く。`clippy::print_stdout` は `print!` / `println!` 系マクロにしか発火しないため、この形は `#[allow]` / `#[expect]` 無しで `-D warnings` を通る。`#[expect(clippy::print_stdout, ...)]` は **付けない**（lint が発火せず `unfulfilled_lint_expectations` が `-D warnings` で hard error になる）

## 2. アーキテクチャ原則

### A-001: 境界層は薄く保ち、外部世界の読み取りをそこに閉じる

**原則**: プロセス環境・ファイル I/O・ネットワークなど外部世界の状態を読むのは境界層だけとし、解決・判断のロジックには値を引数で渡す。`main.rs` は `lib.rs` の `main_entry()` を呼ぶだけに保ち、ロジックを二重実装しない。

**適用範囲**: すべてのモジュール

**検証方法**:

- [ ] `main.rs` にロジックが無い
- [ ] 環境変数・設定ファイルを読む処理が境界の型に集約されている（例: `logging::LogEnv::from_process`）
- [ ] 解決ロジックがプロセス環境を書き換えずに単体テストできる

**違反例**:

- 解決ロジックの内部で `std::env::var` を直接呼ぶ。テストが実行環境に依存し、edition 2024 では `std::env::set_var` が unsafe かつ結合テストはスレッド並列に走るため、テスト側で回避できない
- `main.rs` に処理を書き、lib 側と二重に実装する

**準拠例**:

- `LogEnv::from_process()` で読み、`resolve_directives(verbose, &env)` に値として渡す
- テストは `LogEnv::default()` を注入する。子プロセスを spawn するテストは `bin()` が `LogEnv::NAMES` を回して環境変数を外す（名前の真実を読み取り側の 1 箇所に置く）

---

### A-002: セキュリティに関わる仕組みを自作しない

**原則**: TLS・暗号・シークレット保存・認証は既存の実装に委ね、自作しない。採用する実装は固定し、機械的に検証する。

**適用範囲**: すべての依存追加

**検証方法**:

- [ ] TLS は rustls（`reqwest` は `default-features = false` + `rustls-tls`）
- [ ] `openssl` / `openssl-sys` が依存グラフに無い（`deny.toml` の `[bans] deny`）
- [ ] シークレットの保存は OS の機構を使い、独自のファイル形式や暗号を作らない
- [ ] `cargo deny --all-features check advisories bans licenses sources` が通る

**違反例**:

- 独自のトークン暗号化・独自のファイル形式でのトークン保存
- `reqwest` を既定 features で入れる。native-tls 経由で `openssl-sys` を引き込み `audit.yml` が PR で落ちる
- 依存を git 参照やバージョンのワイルドカードで入れる

**準拠例**:

- OS のセキュアな保存領域を扱う既存クレートを使う
- 依存を追加する前に `deny.toml` の `[bans]` / `[licenses]` / `[sources]` を確認する

## 3. 開発手法原則

### D-001: 外形をテストで固定する

**原則**: すべてのサブコマンドについて、終了コードと stdout / stderr の出し分けを結合テストで固定する。バイナリを spawn して外から検証する。

**適用範囲**: すべてのサブコマンド、CLI の入出力に関わる変更

**検証方法**:

- [ ] 各サブコマンドに終了コードを検証する結合テストがある
- [ ] 失敗時に stdout が空であることを検証している
- [ ] 結合テストが実行環境の環境変数に影響されない
- [ ] `cargo test --locked --all-features --all-targets` が 3 OS で通る

**違反例**:

- 終了コードを検証しないテスト
- ライブラリ API を直接呼ぶだけで、stdout / stderr の出し分けを検証しない
- テストの中で `std::env::set_var` / `remove_var` を呼ぶ

**準拠例**:

- `assert_cmd` でバイナリを spawn し、`.failure()` と `.stdout(is_empty())` を並べる
- 純粋なロジックは各モジュールの `#[cfg(test)] mod tests` で単体テストする

**補足**: カバレッジの数値目標はこの原則に含めない。計測を導入していない数値を非交渉原則にすると初日から違反状態になるため、「メトリクスとモニタリング」節の目標として扱う。

---

### D-002: 新機能は仕様書から始める

**原則**: 新しいサブコマンドや外部 API 連携を追加するときは、PRD → 仕様書 → 設計書を先に作る。既存の外形を変えない軽微な変更はこの限りではない。

**適用範囲**:

| 区分 | 対象 |
|:---|:---|
| **必須** | 新規サブコマンドの追加 / 外部 API との連携 / 認証情報の扱いに関わる変更 / 配布ターゲットの増減 / 既存サブコマンドの後方非互換な変更 |
| **不要** | バグ修正 / ドキュメント修正 / コメント修正 / 後方互換なオプション追加 / 外形が変わらないリファクタリング |

**検証方法**:

- [ ] 必須に該当する変更に `.sdd/requirement/` の PRD がある
- [ ] `.sdd/specification/` に `*_spec.md` と `*_design.md` がある
- [ ] 仕様書が実装より新しい（実装前に更新されている）

**違反例**:

- 新規サブコマンドを仕様書なしで実装する
- 仕様書が古いまま実装を進める

**準拠例**:

- 必須側: `/generate-prd` → `/generate-spec` で PRD と仕様書を確定させてから、`CLAUDE.md` の「サブコマンドを追加する手順」に入る
- 不要側: バグ修正・外形が変わらないリファクタリングは `CLAUDE.md` の「コードスタイル」「テスト構成」節だけで進める。後方互換なオプション追加は加えて「ドキュメント」節（両 README の表を更新）に従う

## 開発標準

### コード品質

| 標準 | 要件 | ツール | 適用方法 |
|:---|:---|:---|:---|
| **フォーマット** | 差分ゼロ（設定は `rustfmt.toml`） | rustfmt | CI（fmt ジョブ） |
| **Lint** | 警告ゼロ（`clippy::all` を deny + 個別 lint を warn） | clippy | CI（clippy ジョブ、`-D warnings`） |
| **ドキュメント警告** | intra-doc link 切れゼロ | rustdoc | CI（docs ジョブ、`RUSTDOCFLAGS="-D warnings"`） |
| **サプライチェーン** | advisories / bans / licenses / sources すべて ok | cargo-deny | `audit.yml`（週次 cron 併用） |
| **依存の固定** | `Cargo.lock` をコミットし、cargo でビルド／検査するジョブは `--locked` | cargo | CI（clippy / test / MSRV / cross-check / docs） |
| **MSRV** | `Cargo.toml` の `rust-version` で `cargo check` が通る | rustup | CI（msrv ジョブ） |

> `cargo fmt` は `--locked` を受け付けないため fmt ジョブは対象外。dist-guard は cargo を実行しない grep のみのジョブ。

### ドキュメント

| 標準 | 要件 | 配置場所 | 更新頻度 |
|:---|:---|:---|:---|
| **仕様書** | D-002 の必須に該当する機能に `*_spec.md` が必要 | `.sdd/specification/` | 実装前 |
| **設計書** | D-002 の必須に該当する実装に `*_design.md` が必要 | `.sdd/specification/` | 設計フェーズ |
| **README** | 英語版と日本語版の 2 本立て。**片方だけ更新しない** | プロジェクトルート | CLI 変更時 |
| **CHANGELOG** | 英語。`## [X.Y.Z] - YYYY-MM-DD` 形式を厳守（dist が抽出する） | プロジェクトルート | 利用者向け変更時 |
| **開発ガイド** | 原則の具体化と「踏むと壊れる」箇所。具体値の二次情報はここに置く | `CLAUDE.md` | 構成変更時 |
| **記述の裏取り** | ファイル・設定・コマンドへの断定は実機で確認してから書く | すべて | 記述するたび |

### テスト

| 標準 | 要件 | 適用方法 | 例外 |
|:---|:---|:---|:---|
| **結合テスト** | 全サブコマンドの終了コードと stdout / stderr を検証 | `cargo test`（3 OS） | - |
| **単体テスト** | 純粋なロジックは各モジュール内で検証 | `cargo test --lib` | - |
| **doc テスト** | doc コメントの例が通る | `cargo test --doc` | - |
| **環境独立性** | 実行環境の環境変数に影響されない | `bin()` の `env_remove` | - |
| **スナップショット** | まとまった出力は `insta` で固定。可変値は必ずマスクする | cargo-insta | 現状 `tests/` は未導入 |
| **カバレッジ** | 目標値は未設定（計測を未導入） | - | 導入するまで原則に含めない |

### セキュリティ

| 標準 | 要件 | 適用方法 | レビュー頻度 |
|:---|:---|:---|:---|
| **シークレット管理** | コードに含めない / stdout に出さない / プロセス引数に載せない | B-001 の検証項目 | 各 PR |
| **入力検証** | 外部入力（stdin・API レスポンス・ファイル）を検証する | コードレビュー | 各 PR |
| **認証** | 業界標準の手法のみ。自作しない | A-002 | 設計フェーズ |
| **TLS** | rustls 固定。`openssl` / `openssl-sys` を禁止 | `deny.toml [bans]` | 依存追加時 |
| **依存関係スキャン** | 重大な脆弱性ゼロ | cargo-deny | 各 PR + 週次 |
| **ログの遮断** | HTTP レイヤのトレースを既定で `warn` に固定 | `logging.rs` | 各 PR |

## アーキテクチャ制約

### レイヤ構成

```
main.rs（エントリ: lib.rs::main_entry() を呼ぶだけ）
      ↓
lib.rs::main_entry（バイナリ層: 引数パース / ログ初期化 / エラー表示 / 終了コードへの変換）
      ↓
lib.rs::run（サブコマンドのディスパッチ）
      ↓
機能モジュール（cli / logging / error / 将来の tts・認証情報）
      ↓
外部（MiniMax API / OS のセキュアな保存領域 / ファイルシステム）
```

**ルール**:

- 層をスキップしてはならない（`main.rs` は `lib.rs` にのみ依存し、機能モジュールを直接呼ばない）
- 循環依存禁止
- 外部世界への到達は最下層に閉じる
- 各層は単一責任

### 技術スタック制約

| レイヤー | 許可される技術 | 禁止事項 | 理由 |
|:---|:---|:---|:---|
| **引数パース** | clap（derive） | 手書きの引数パーサ | help / version の一貫性、`--version` の真実を `Cargo.toml` に集約 |
| **ログ** | tracing + tracing-subscriber（stderr） | `println!` による診断出力 | B-002 |
| **エラー** | thiserror（ライブラリ層）/ anyhow（バイナリ層） | バイナリ層より下での型無しエラーの恒久化 | 層の責務分離 |
| **HTTP / TLS** | reqwest（`default-features = false` + `rustls-tls`） | native-tls / openssl / openssl-sys | A-002。`deny.toml` でビルド前に禁止 |
| **Windows API** | windows-sys | windows | bloat（`deny.toml [bans]`） |
| **テスト** | assert_cmd / predicates / insta | 自前の golden ファイル | 可変値のマスクが必要 |
| **配布** | cargo-dist（`dist`） | `release.yml` の手編集 | 生成物であり、手編集すると PR の `plan` ジョブが落ちる |

**現フェーズの例外（エラー）**: `lib.rs::run()` は暫定的に `anyhow::Result` を返し、未実装スタブは `anyhow::bail!` を使う。TTS 実装時に `run()` を型付きエラーへ寄せ、`anyhow` は `main_entry` に閉じる（`CLAUDE.md` の「エラー処理の層分け」と同じ内容）。

**例外プロセス**: GitHub Issue で理由と影響範囲を提案し、`deny.toml` と `CLAUDE.md` を同じ PR で更新する。

### モジュール構成

```
src/
├── main.rs      # エントリ。main_entry() を呼ぶだけに保つ
├── lib.rs       # 公開 API。main_entry() と run() を持つ
├── cli.rs       # clap の引数定義（CLI の真実の源）
├── error.rs     # thiserror によるライブラリ層エラー型（現状は骨格のみで未使用）
└── logging.rs   # tracing-subscriber 初期化。環境変数の読み取り境界
tests/
├── cli.rs       # 結合テスト（バイナリを spawn）
└── common/      # 共有ヘルパー（bin() など）
```

**依存ルール**:

- `main.rs` は `lib.rs` にのみ依存する
- `lib.rs` は機能モジュールに依存する
- 機能モジュール同士の相互依存を作らない
- 外部世界の読み取りは境界の型に集約する（A-001）

## 意思決定フレームワーク

技術的トレードオフに直面した場合、以下の順序で優先順位付けします：

1. **セキュリティ** - 認証情報が漏れないか？
2. **正確性** - 仕様を満たしているか？
3. **シンプルさ** - 最もシンプルな解決策か？
4. **保守性** - 保守可能か？
5. **パフォーマンス** - 十分に高速か？
6. **開発者体験** - 作業しやすいか？

セキュリティを正確性より上に置いているのは、B-001 が原則階層の最上位にあるためです。

**タイブレーカー**: 後で変更しやすい方を選択する。ただし B-001 に関わる判断は「後で直せる」を理由に妥協しない。

**実装量で設計を決めない**: 「実装が大きそうだからコメントで済ませる」「コストが高いから呼び出し側で対処する」といった判断をしない。実装量は着手するまでわからず、推定で設計を曲げるとやり直しになる。

## 4. 技術制約

### T-001: 実行時に落ちる余地を残さない

**原則**: パニックしうる経路を実装から排除し、失敗は型で表現する。

**適用範囲**: すべてのソースコード（テストコードを除く）

**検証方法**:

- [ ] `unsafe` を書かない（`[lints.rust] unsafe_code = "forbid"`）
- [ ] `unwrap()` / `expect()` をテスト以外で使わない。**現状 `src/*.rs` の本番コードは 0 件なので、この状態を維持する。** どうしても必要なときの例外はコンパイル時に決まるリテラルのパースだけに限る
- [ ] `todo!()` / `dbg!()` を残さない。未実装は `anyhow::bail!` でスタブする（この `anyhow::bail!` は技術スタック制約の「現フェーズの例外（エラー）」として許容する）
- [ ] `cargo clippy --locked --all-targets --all-features -- -D warnings` が通る
- [ ] `Cargo.toml` の `rust-version` で `cargo check --locked --all-targets --all-features` が通る

**違反例**:

- 実行時入力・I/O・環境依存の値に `unwrap()` / `expect()`
- `todo!()` を残す（`clippy::todo` + `-D warnings` で hard error）
- `panic!` のメッセージを利用者に見せる

**準拠例**:

- `thiserror` で型付きエラーを定義し、`main_entry` が `anyhow` で受けて終了コードに変換する（TTS 実装時の到達形。現状は技術スタック制約の「現フェーズの例外（エラー）」を参照）
- `Option` / `Result` を素直に伝播させる

**注意**: `clippy::unwrap_used` / `clippy::expect_used` は有効化していないため、`unwrap` / `expect` の禁止は機械検出されません。レビューで見ます。

### v1.1.0 (2026-07-29)

**HTTP レイヤの遮断を実装レベルで完成させ、B-001 の検証方法を強められる形に更新**

`/simplify` の 4 観点レビュー（Altitude 観点）で、`logging.rs` の HTTP レイヤ `warn` 固定が
`add_directive` による後付け上書きであり、`hyper::proto=trace` のような**より深い target で貫通する**
ことが実測で確認された（capture ハーネスで `authorization: Bearer leaked` の出力を再現）。
しかも当時のテストは「貫通すること」を固定していたため、`reqwest` を追加しても CI は green のままで、
「導入 PR で直す」という約束は人の記憶にしか依存していなかった。

- `EnvFilter` と `filter::Targets` を `FilterExt::and` で AND 結合する形に置き換えた。`Targets` は
  target を `::` 区切りの接頭辞で照合するため、グローバル指定・同名 target・深い target の
  いずれでも貫通しない
- B-001 の検証方法から「貫通する制約を承知している」を削除し、「どんな directive を与えても
  `warn` より下に開かない」と「新しい HTTP / TLS クレートを `HTTP_LAYER_CRATES` に追加した」に置き換えた
- 「導入 > 既存コード向け」の未達を 3 件から 2 件に減らした
- 副次的に本番コードの `unwrap` / `expect` が 0 件になったため、T-001 の検証項目をその状態の維持に強めた
- A-001 の準拠例を実装に合わせた（入口は `init(verbose, &LogEnv)` の 1 本、テストは `LogEnv::default()`、
  環境変数名の真実は `LogEnv::NAMES`）
